# RepoWatch — original design notes

This document records the early design. For the current beta scope, permissions and
installation instructions, see [README](README.md) and [architecture](docs/architecture.md).

Daily monitoring of all public repositories of a GitHub account, with history over time and a dashboard.

## Problem

GitHub only shows totals (stars, release downloads) or 14-day windows (traffic). There is no history,
no single view across all repositories, and the raw numbers are misleading (e.g. hundreds of clones in a
few days, almost all generated by GitHub Actions checkouts).

Goal: understand **whether real people** discover and use the projects, and where they come from.

## Repositories to monitor

All public repositories of the configured account (`GITHUB_OWNER`), discovered automatically on every
run (no hardcoded list). Forks are excluded (configurable).

## Access

- GitHub **fine-grained personal access token**: resource owner = the monitored account,
  "All repositories" (or selected ones), repository permissions **Administration: read** (traffic) +
  **Metadata: read** (default). Nothing else.
- Since July 2026 the stargazers list is limited to admins/collaborators (write-capable token).
  By default new stars are derived from the daily count; an optional separate token
  (`GITHUB_STARS_TOKEN`) enables names and dates.
- Token in `.env` (`GITHUB_TOKEN=...`), never committed. `.env` is in `.gitignore`; `.env.example` is provided.
- Authenticated rate limit: 5,000 requests/hour, more than enough.

## Data collected (once a day)

| Data | Endpoint | Notes |
|---|---|---|
| Repository list | `GET /users/{owner}/repos` | metadata, `fork`, `archived` |
| Stars, forks, watchers, open issues | `GET /repos/{o}/{r}` | daily snapshot |
| Stargazers with date | `GET /repos/{o}/{r}/stargazers` (header `Accept: application/vnd.github.star+json`) | to detect *new* stars and who |
| Release asset downloads | `GET /repos/{o}/{r}/releases` | cumulative `download_count` per asset → store snapshot, compute delta |
| Daily views | `GET /repos/{o}/{r}/traffic/views?per=day` | count + uniques, last 14 days |
| Daily clones | `GET /repos/{o}/{r}/traffic/clones?per=day` | count + uniques, last 14 days |
| Referring sites | `GET /repos/{o}/{r}/traffic/popular/referrers` | top 10, aggregated over 14 days → daily snapshot |
| Popular pages | `GET /repos/{o}/{r}/traffic/popular/paths` | top 10, aggregated over 14 days → daily snapshot |
| Issues / PRs / comments | `GET /repos/{o}/{r}/issues?state=all&since=...` | distinguish owner from external authors |
| CI runs | `GET /repos/{o}/{r}/actions/runs?created=...` | number of runs + jobs with checkout, to estimate "noise" clones |

Optional: PyPI downloads for published packages (pypistats.org API), configured explicitly per repository.

### Key rules

- **Upsert per day**: views/clones arrive as a 14-day series → upsert on `(repo, date)`, so repeated
  runs or skipped days create neither duplicates nor gaps (up to 14 days of delay can be recovered).
- **Deltas from cumulative counters**: stars and asset downloads are totals → store a daily snapshot
  and compute the difference.
- **CI noise on clones**: show clones next to the day's CI checkout jobs; never present them as "users".
- **Owner activity**: exclude the owner (and bots) from issues/comments/stargazers when counting
  external signals.

## Storage

SQLite (`data/repowatch.db`). Tables:

- `repos(name, description, created_at, fork, archived, first_seen, last_seen, ...)`
- `repo_snapshots(repo, date, stars, forks, watchers, open_issues)`
- `traffic_daily(repo, date, views, views_uniques, clones, clones_uniques)` — PK `(repo, date)`
- `referrers_snapshots(repo, date, referrer, count, uniques)`
- `paths_snapshots(repo, date, path, title, count, uniques)`
- `releases(repo, tag, name, published_at, prerelease, html_url)`
- `release_asset_snapshots(repo, date, tag, asset, download_count)`
- `stargazers(repo, user, starred_at)`
- `forks(repo, full_name, owner, created_at)`
- `activity(repo, kind, gh_id, number, user, is_owner, is_bot, title, url, created_at)`
- `ci_runs(repo, run_id, date, event, status, jobs, checkout_jobs)` + view `ci_daily`
- `pypi_daily(repo, package, date, downloads)`
- `events(id, key, repo, date, type, detail, url, seen)` — notable events generated by the collector
- `collector_runs(started_at, finished_at, repos, errors, error_log)`

## Notable events

Generated by comparing today's snapshot with the previous one:

- new star (with user), new fork, new watcher
- new issue / PR / comment from an external user
- new release downloads (e.g. "+5 app.apk v1.0.0")
- new referrer never seen before (e.g. "first visitors from reddit.com")
- spike in unique visitors (e.g. > 3× the average of the previous 14 days)
- new public repository detected

On the first run for a repository its existing history is imported as a baseline without generating events.

## Dashboard

Single private view, readable on a phone too:

1. **What's new feed** at the top: recent events not yet seen.
2. **Summary table** of all repositories: stars (Δ), total downloads (Δ), unique visitors,
   clones vs CI runs, top referrer, latest release, external activity, last push.
3. **Repository detail**: charts over time of views/uniques, clones vs CI checkouts, cumulative stars,
   downloads per release/asset; tables of referrers and popular pages.
4. Period filter: 7 / 14 / 30 / 90 days / all.

## Architecture

- **Collector**: Python script (`httpx`), run daily by cron. Idempotent, tolerant to errors in a single repository.
- **Dashboard**: small FastAPI app serving a JSON API and a static page with charts, reading from SQLite,
  bound to localhost and protected by basic auth and/or a reverse proxy.
- **Notifications (future, optional)**: push notable events to a chat service (e.g. Telegram).

## Out of scope (for now)

- In-app analytics.
- Repositories of other accounts/organisations in a single instance.
- Private repositories (the token may be able to read them, but only public ones are monitored).
